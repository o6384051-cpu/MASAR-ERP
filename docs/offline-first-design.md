# تصميم التشغيل دون اتصال — MASAR ERP

## الهدف وحدود السلامة
يجب أن يستطيع المستخدم مواصلة إدخال مسودات العمليات عند انقطاع الإنترنت، ثم إرسالها إلى خادم Frappe عند عودة الاتصال. لا يعني وضع عدم الاتصال أن دفتر الأستاذ أو الأرصدة أو المخزون أصبحت متاحة للترحيل محلياً، ولا يجوز عرض بيانات قديمة على أنها أرصدة لحظية.
المبدأ المحاسبي الحاكم: لا ترحيل مالي نهائي ولا اعتماد فاتورة أو سند ولا تحديث مخزون نهائي على الجهاز. الخادم وحده يتحقق من الصلاحيات والفترة المالية والضرائب والمخزون والأسعار ثم ينشئ مستند ERPNext القياسي.

## مستويات التشغيل
1. متصل: جميع وظائف ERPNext المعتادة، مع بيان آخر مزامنة وحالة الخادم.
2. اتصال متقطع: حفظ المسودات المحلية في IndexedDB، وإظهار حالة «بانتظار المزامنة» ومعرّف العملية.
3. غير متصل: واجهة أساسية مخزنة مؤقتاً، وإنشاء/تعديل مسودات محلية فقط. تعطيل الترحيل والاعتماد والطباعة التي تتطلب بيانات حديثة، والتقارير الحية، والتحصيل الإلكتروني، والتكاملات الخارجية.
4. استعادة الاتصال: إرسال العمليات بالترتيب، مع مفتاح idempotency ثابت لكل عملية، والتحقق من المستخدم والشركة والصلاحيات على الخادم، ثم إرجاع نتيجة كل عملية منفردة.

## قواعد المزامنة الضرورية
- لكل عملية UUID ثابت لا يتغير عند إعادة المحاولة.
- الخادم يسجل UUID فريداً قبل تنفيذ الأثر المالي، ويعيد النتيجة السابقة عند تكرار الطلب.
- لا تستخدم ساعة الجهاز لتحديد ترتيب الترحيل أو تاريخ القيد المعتمد.
- تحفظ المسودة المحلية مع الشركة ونوع المستند وإصدار المخطط والطوابع الزمنية والحمولة وحالة المزامنة ونسخة المستند الأساسية عند التعديل.
- إذا تغير المستند على الخادم منذ تنزيله، تُحوّل العملية إلى حالة تعارض ولا يتم الكتابة فوق البيانات بصمت.
- التحقق من صلاحية المستخدم والشركة والفرع ومركز التكلفة يتم على الخادم لكل عملية.
- تُرفض الحقول غير المسموح بها وحقول حالة الترحيل والأرصدة وحسابات الأستاذ وأي حقول نظامية حساسة من العميل.
- العمليات غير الصالحة لا تمنع مزامنة بقية الدفعة؛ تُعرض أسباب الرفض بوضوح.
- لا تحذف المسودة المحلية حتى يؤكد الخادم نجاح حفظها أو يقرر المستخدم حل التعارض.
- لا تُخزّن كلمات المرور أو مفاتيح API أو ملفات الجلسات في IndexedDB أو Cache Storage.

## سياسة التخزين المؤقت
- يسمح بتخزين ملفات الواجهة العامة فقط بعد مراجعة مساراتها.
- يمنع تخزين واجهات API وصفحات الحسابات والتقارير والمرفقات وملفات المستخدمين والاستجابات التي تحمل بيانات مالية أو شخصية.
- لا يُستخدم CacheFirst لبيانات ERPNext الخاصة. يجب أن تكون استجابات المستخدمين والشركات network-only أو no-store.
- تُشفّر المسودات المحلية بمفتاح جلسة/جهاز مُدار بطريقة آمنة قبل اعتماد التخزين طويل الأجل. إذا تعذر ضمان حماية المفتاح على الجهاز، يُمنع حفظ البيانات الحساسة محلياً.
- يدعم المستخدم تسجيل الخروج ومسح بيانات الجهاز وإبطال مخزن الجهاز.

## مراحل التنفيذ والقبول
### O1 — أساس الواجهة
- كشف حالة الاتصال والخادم وآخر مزامنة.
- واجهة offline fallback عامة لا تعرض بيانات مالية.
- قائمة عمليات محلية وحالاتها دون بيانات حساسة في السجلات.
- لا تعتبر هذه المرحلة دعماً كاملاً للعمل المحاسبي دون اتصال.
### O2 — مسودات آمنة
- IndexedDB versioned schema.
- إنشاء وتعديل مسودات محددة فقط، مع تشفيرها ومراعاة تعدد المستخدمين على الجهاز.
- اختبارات إغلاق المتصفح وإعادة فتحه وفقدان الاتصال والمساحة التخزينية.
### O3 — بوابة مزامنة خادمية
- DocType لسجل idempotency/receipts بقيود فريدة.
- API allowlist لأنواع العمليات والحقول المسموح بها.
- فحص الصلاحيات والشركة والفترة المالية ومقارنة النسخ.
- منع الترحيل النهائي من العميل واختبارات إعادة الطلب والتعارض.
### O4 — قبول محاسبي
- اختبار انقطاع الاتصال أثناء الإرسال وبعد حفظ الخادم وقبل وصول الرد.
- اختبار إعادة إرسال نفس UUID عدة مرات دون تكرار القيد أو الفاتورة.
- اختبار مستخدمين وشركتين وصلاحيات مختلفة.
- اختبار الاستعادة والنسخ الاحتياطي ومسح بيانات الجهاز.

## ما لا يجوز اعتباره منجزاً
لا يكفي Service Worker أو مؤشر اتصال أو تخزين نموذج في المتصفح لإعلان أن النظام يعمل محاسبياً دون إنترنت. لا تُعلن ميزة Offline Accounting مكتملة حتى تنجح اختبارات O2–O4 على موقع Frappe/ERPNext فعلي وقاعدة بيانات فعلية.
