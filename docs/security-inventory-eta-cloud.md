# متطلبات MASAR-ERP: الصلاحيات والمخزون والفاتورة الإلكترونية والسحابة

هذه المتطلبات جزء أساسي من المنتج. هي مواصفات تنفيذ واختبار وليست ادعاءً بأن الوظائف قد اكتملت.

## 1. نظام صلاحيات متقدم وسرية البيانات
### نطاق الصلاحيات
- أدوار قابلة للتخصيص: مالك النظام، مدير الشركة، المدير المالي، المحاسب، أمين المخزن، المبيعات، المشتريات، المراجع، ومستخدم قراءة فقط.
- نطاقات إلزامية للصلاحية: الشركة، الفرع، المستودع، مركز التكلفة، نوع المستند، وحالة المستند.
- فصل صلاحيات العرض والإنشاء والتعديل والحذف والإرسال والاعتماد والترحيل والعكس والطباعة والتصدير والتنزيل.
- منع المستخدم من اعتماد مستند أنشأه إذا كانت سياسة الفصل بين المهام تتطلب معتمداً مستقلاً.
- صلاحيات حقول وسجلات حساسة، مع إخفاء بيانات الرواتب والبنوك والتكلفة وهوامش الربح حسب الدور.
- دعم أقل صلاحية لازمة، ومنع الوصول الافتراضي، والتحقق الخادمي في كل API وعدم الاعتماد على إخفاء الأزرار في الواجهة.
### التدقيق والحماية
- سجل غير قابل للتعديل العادي يثبت المستخدم والتوقيت والعملية والمستند والنتيجة ومصدر الدخول.
- تسجيل محاولات الدخول الفاشلة وتغييرات الأدوار والصلاحيات والتصدير والتنزيل واعتماد المستندات.
- جلسات آمنة، MFA حيثما أمكن، إنهاء الجلسات، وسياسة كلمات مرور واستعادة حساب.
- اختبارات عزل بين شركتين ومستخدمين وفروع ومستودعات، واختبارات منع الوصول المباشر إلى API والمرفقات.
- لا تسجل كلمات المرور أو الرموز أو محتوى المستندات الحساسة في سجلات التطبيق.

## 2. الفاتورة والإيصال الإلكتروني المصري
### التكامل
- بناء موصل مستقل لخدمات مصلحة الضرائب المصرية ETA، مع فصل بيئات الاختبار والإنتاج وإدارة الأسرار والشهادات على الخادم فقط.
- الالتزام بإصدارات SDK ومخططات JSON/XML وقواعد التحقق المنشورة من ETA وقت التنفيذ؛ لا تثبت المخططات أو الأكواد في الشفرة دون آلية تحديث.
- إدارة هوية الممول والنظام والمفوضين وبيانات الوصول وشهادة الختم الإلكتروني/التوقيع حسب متطلبات ETA.
- دعم إرسال المستندات، واستعلام الحالة ونتائج التحقق، واستقبال إشعارات القبول أو الرفض أو الإلغاء، وإعادة المحاولة الآمنة.
- تخزين المعرف الداخلي ومعرف ETA وحالة الإرسال ومعرف الدفعة ووقت الإرسال ونتائج التحقق وأثر كل محاولة.
- دعم الإشعارات/المستندات التصحيحية الملائمة، وربطها بالمستند الأصلي وفق قواعد ETA الحالية.
- عدم إصدار فاتورة ضريبية على أنها معتمدة قبل الحصول على نتيجة الحالة الرسمية المطلوبة من المنظومة.
- عدم إنشاء أرقام أو أكواد ضريبية أو أسعار أو نسب ضريبة افتراضية؛ تُدار البيانات حسب ملف الممول والقواعد الرسمية المعتمدة.
### قبول الامتثال
- اختبارات sandbox/PreProd على بيانات وشهادات اختبار رسمية.
- اختبارات التوقيع والتحقق من سلامة الحمولة والتكويد وتصنيف السلع والخدمات.
- اختبارات الرفض والتأخير وانقطاع الاتصال وإعادة الإرسال دون تكرار المستند.
- اختبار مستندات B2B وB2C بحسب نطاق تسجيل الممول والتزامه، وعدم افتراض أن كل شركة تحتاج النوعين.
- لا يوصف المنتج بأنه متوافق أو معتمد نهائياً قبل نجاح اختبارات التكامل والتحقق من متطلبات الممول الفعلية مع ETA ومحاسب/مستشار ضريبي.
### مراجع رسمية
- ETA SDK: https://sdk.sit.invoicing.eta.gov.eg/
- دليل البدء والتكامل: https://sdk.invoicing.eta.gov.eg/start/
- واجهات API: https://sdk.invoicing.eta.gov.eg/einvoicingapi/
- FAQ والبيئات: https://sdk.invoicing.eta.gov.eg/faq/
- إرسال المستندات: https://sdk.invoicing.eta.gov.eg/einvoicingapi/01-submit-documents/

## 3. إدارة المخزون والمستودعات والجرد بالجوال
### دورة المخزون
- تعريف الأصناف والوحدات والتحويلات والباركود والدفعات والأرقام التسلسلية وتواريخ الصلاحية عند الحاجة.
- مستودعات ومواقع تخزين متعددة، ومخزون افتتاحي، واستلام وصرف وتحويل ومرتجع وتسوية وجرد.
- ربط كل حركة بمستند مصدر ومستخدم ووقت وسبب ومستودع وموقع تخزين.
- تتبع تكلفة المخزون وفق طريقة التقييم المهيأة في ERPNext وعدم حساب التكلفة في واجهة الهاتف.
- سياسات منع الرصيد السالب أو السماح به بموافقة محددة، مع قفل/تحقق خادمي عند ترحيل الحركة.
- تقارير كميات وقيم وحركات وبطاقات صنف وأعمار مخزون وحد إعادة الطلب.
### الجرد عبر الهاتف
- واجهة عربية RTL متجاوبة كتطبيق ويب تقدمي PWA.
- إدخال الجرد يدوياً أو بمسح الباركود/QR عبر كاميرا الجهاز عندما يدعم المتصفح ذلك.
- قوائم جرد محددة مسبقاً حسب الشركة والمستودع ومجموعة الأصناف، مع إخفاء الرصيد الدفتري عن العادّين عند اختيار الجرد الأعمى.
- حفظ قراءات الجرد محلياً عند انقطاع الإنترنت مع UUID لكل قراءة ومستخدم وجلسة جرد.
- مزامنة القراءات عند عودة الاتصال، وكشف القراءات المكررة والتعارضات، واعتماد فروق الجرد وترحيلها على الخادم فقط.
- إظهار وقت آخر مزامنة والتنبيه بوضوح أن الكميات المحلية غير معتمدة حتى قبولها خادمياً.
### اختبارات القبول
- اختبار تعدد المستخدمين على الصنف والمستودع نفسه، والتكرار، وفقد الشبكة، والباركود غير المعروف، ووحدات القياس.
- اختبار عزل المخازن بين الشركات والفروع.
- مطابقة قيمة المخزون مع القيود المحاسبية بعد الترحيل.

## 4. النظام المحاسبي السحابي
- استضافة Frappe/ERPNext على بنية خادمية مدارة، مع قاعدة بيانات دائمة ونسخ احتياطية مشفرة ومختبرة الاستعادة.
- HTTPS، إدارة أسرار على الخادم، صلاحيات وصول للبنية، تحديثات أمنية ومراقبة وتنبيهات.
- تعدد الشركات والفروع مع عزل البيانات والصلاحيات؛ لا يكفي فصل الواجهة فقط.
- دخول آمن من الهاتف والحاسوب، واجهة RTL متجاوبة، ودعم جلسات متعددة وفق سياسة المؤسسة.
- نسخ احتياطي دوري لقاعدة البيانات والملفات والمرفقات، مع تحديد RPO/RTO واختبار استعادة موثق.
- مراقبة صحة الخدمة والمهام الخلفية وطوابير المزامنة وأخطاء التكامل، مع سجلات لا تكشف أسراراً.
- خطة ترقية وترحيل واختبار rollback، وبيئة staging قبل الإنتاج.
- وضع عدم الاتصال يحفظ مسودات/قراءات محددة فقط؛ التقارير والأرصدة المعتمدة والاعتمادات والترحيل النهائي تحتاج اتصالاً وتحققاً خادمياً.

## 5. بوابات إطلاق إلزامية
1. اختبارات صلاحيات API وعزل الشركات والمرفقات.
2. دورة محاسبية متكاملة ومطابقة الأستاذ والمخزون.
3. اختبارات ETA على PreProd وإقرار نطاق الالتزام الخاص بالممول.
4. اختبارات الجرد على هاتف فعلي أثناء الاتصال والانقطاع ثم المزامنة.
5. اختبار نسخ احتياطي واستعادة، وفحص أمني، ومراقبة، وتجربة قبول مستخدم.
6. لا نشر إنتاجي ولا ادعاء جاهزية قبل توثيق نتائج هذه الاختبارات.
